# Анкета в профиле, эффекты и экипировка

## Сценарий

Во вкладке «Ролевая» профиля пользователя показан список доступных персонажей. По умолчанию выбирается активный персонаж из загруженной страницы, иначе первый. Переключатель загружает только выбранную анкету. Отдельной страницы персонажа нет. После успешного создания мастер переходит во вкладку «Ролевая» профиля владельца с параметром ?character=ID, который выбирает новую анкету среди доступных персонажей этого профиля. При повторном открытии завершённого мастера есть ссылка «Открыть персонажа в профиле».

Анкета использует тот же CharacterSheet, что итог мастера. В профиле добавляются кнопки действий; в мастере анкета остаётся только для чтения. Числа приходят из общего CharacterCalculationBuilder — интерфейс не выполняет повторный расчёт.

Кнопка «Эффекты» открывает список эффектов от полученных перков и экипированных магических вещей. У каждой записи показаны величина, описание, источник, условие, область и способ применения. Текстовые эффекты не получают фиктивное число. Условные эффекты не объявляются уже прибавленными к параметрам. Обычная броня учитывается отдельным полем защиты и не превращается в магический эффект.

## Видимость и права

Общее право roleplay.view вместе с viewForum необходимо для списка и отдельного чтения.

- Владелец видит свои незавершённые и завершённые анкеты.
- Другие пользователи с правом просмотра видят персонажей active/dead/archived только при literature_approved и одобренной технической части.
- Администратор и сотрудник с отдельным правом roleplay.moderate видят незавершённые анкеты через профиль.
- Право roleplay.moderate даёт просмотр и действия независимой проверки частей; подробности — в документе 15.
- Экипировать/снимать может только вошедший владелец персонажа со статусом active. Выбор персонажа в переключателе сам по себе не даёт прав владельца.
- Администратор и модератор не получают права менять чужую экипировку.
- Чужая закрытая анкета и отсутствующий ID возвращают одинаковую ошибку 404.

Механическое состояние создаётся серверным проверенным планом, но обе части проходят независимую модерацию. mechanics_status и literature_status хранят решения, status определяет жизненный цикл; публикация требует обоих одобрений. Смена литературной ссылки администратором сохраняет одобрение по прежней договорённости.

## API

GET /api/roleplay/users/{userId}/characters?before=ID возвращает не более 30 строк и next_before. Фильтр видимости применяется до ограничения выборки. Новые персонажи не сдвигают курсор уже загруженной страницы.

GET /api/roleplay/characters/{id} возвращает snapshot, calculation, минимальные lookups характеристик и permissions.can_equip. В заголовок не попадают служебные данные создания и правила расы. Отключённые уже полученные определения остаются читаемыми.

POST /api/roleplay/characters/{id}/equipment принимает только:

- operation_key: UUID v4;
- revision: версия персонажа;
- catalog_revision: версия справочников;
- instance_id: ID конкретной строки инвентаря, не определения предмета;
- equipped: настоящее логическое значение.

Ответ содержит заново рассчитанную актуальную анкету. Ответы API private, no-store. Сервер не доверяет permissions из клиента.

## Правила операции

Лимит относится к типу предмета, считается по отдельным экипированным экземплярам: 0 — без лимита, -1 — нельзя экипировать. Положительный лимит проверяется до изменения. Снятие разрешено даже после отключения типа или уменьшения лимита.

При экипировке стопки количество больше 1 уменьшается на один и создаётся отдельный экипированный экземпляр с quantity=1. Если количество уже 1, переключается его флаг. Снятая вещь остаётся отдельной строкой инвентаря: автоматическое объединение стопок в эту операцию не добавлялось. Вес всегда считается по всему инвентарю ровно один раз.

Наличие владения оружием не запрещает экипировать вещь; оно ограничивает доступные атаки в существующем CharacterAttackBuilder. Отключённое определение не отнимает уже принадлежащую вещь.

Порядок блокировок: справочники -> аккаунт -> персонаж. Запись вещи, версии, операции и события выполняется одной транзакцией. Перед фиксацией проверяется новый снимок/расчёт; ошибка откатывает всё. Изменение экипировки не меняет версию справочников.

Повтор точно той же команды возвращает результат операции без повторной записи. Повтор того же UUID с другим телом запрещён. Клиент сохраняет UUID/тело после потери ответа и блокирует другие действия до повтора или обновления. При конфликте версии/прав нужно заново загрузить анкету.

## Проверки и границы

tests/profile-scenarios.php запускается внутри check-base-catalogs.php на временных таблицах с проверенным случайным префиксом. Макеты владельца/посетителя/модератора не записываются в users. Проверяются скрытые анкеты, публичное чтение, права, лимиты -1/0/1, разделение стопки, вес/мана/броня, конфликты, повторы, откат при ошибке истории, реальные контроллеры и курсор.

tests/check-profile-client.cjs выполняет настоящий Mithril из локальной карты ядра. Проверяет разметку анкеты/окна, кнопки, переключение, запоздавшие ответы, сетевой повтор с прежним UUID, конфликт и закрытие страницы. Это проверка поведения/разметки, не визуальная проверка в браузере.

Литературная тема и проверка обеих частей подключены следующим реализованным этапом: [документ 15](15-application-review.md). Прокачка и расход ресурсов остаются отдельными этапами.

Новый пакет по-прежнему не установлен на рабочий форум. Подключение и перенос данных требуют отдельного согласованного этапа.

## Экипировка по клику

Владелец активного персонажа нажимает карточку в инвентаре, чтобы надеть или снять предмет. После подтверждения сервера надетый экземпляр получает зелёную рамку и галочку. Клик по маленькой карточке в экипировке снимает предмет. У этих карточек нет зелёной рамки и галочки — отметка остаётся только в инвентаре. Enter и пробел работают так же.

CharacterSheet получает необязательный itemControl из ProfilePanel и использует общую SelectableEntityCard. Для посетителя рамка остаётся видимой, но управление отсутствует. Расчёт и лимиты проверяет прежний CharacterEquipment; UI не меняет состояние заранее.

Размеры маленьких карточек заданы в resources/forum.css в блоке RpSheet-equipment: ширина контейнера 160 px и высота карточки 141 px. ItemCard формирует их подсказки из свойств и перезарядки; внешний вид в них не включается. У полной карточки подсказка внешнего вида сохраняется.

## Верхняя панель и вкладки

ProfilePanel управляет верхней панелью, переключателем персонажей и вкладками. CharacterSheet не рисует декоративный баннер и не получает кнопки через toolbar: он используется как в профиле, так и в итоге мастера.

- Пока status = creating, ReviewPanel показывает серую компактную панель с двумя независимыми статусами, значками, счётчиком одобренных частей и разрешёнными действиями. После активации панель исчезает.
- Для активного персонажа доступны «Персонаж», «Обучение», «Крафт». Всё существующее управление, включая развитие и экипировку, остаётся в «Персонаже». Две другие вкладки показывают «В разработке» и не отправляют игровых команд.
- Смена персонажа сбрасывает вкладку и выделенную характеристику. Снятие активации также возвращает вкладку «Персонаж».
- В одной строке расположены выбор персонажа, ссылка на литературную анкету, история, выдачи, эффекты и обновление. Кнопки-значки имеют названия для подсказок и вспомогательных технологий.
- CharacterHistoryModal показывает уже полученные события в компактном прокручиваемом окне. Права доступа и состав истории по-прежнему определяются сервером.
- RpDevelopment-confirm--reserved сохраняет место под кнопки повышения и изучения даже без выбранной записи. Стоимость повышения остаётся на кнопке.
- Цвет и полупрозрачный фон значка раздела задаются общей переменной --rp-section-color в resources/forum.css. Имена всех новых значков находятся в resources/presentation/icons.json; локальная замена мешочка остаётся в icons.local.json.
- Компоновка панели проверки находится в resources/application.css. В стилях используются обычные ограничения высоты, совместимые со сборщиком Less в Flarum.

Переключатель персонажа имеет ширину 210 px на широком экране и собственный шеврон из icons.json. На телефоне поле занимает доступную ширину. Используется настоящий select: клавиатура и системный список сохраняются, шеврон не перехватывает указатель.

Кнопки-значки используют штатный Button--icon, который убирает пустую подпись ядра и её зазор. Плашки урона центрируют подпись по вертикали всей строки, даже когда соседнее значение переносится на две строки.
