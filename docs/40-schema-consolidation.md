# Единая миграция и подготовка проекта

## Что изменено

В `migrations/` оставлен один файл — `2026_10_02_000001_create_base_catalogs.php`. Он сразу создаёт итоговую схему: 35 таблиц, включая события, награды, проверки, литературу и обучение. На чистом форуме персонажей и наполненных справочников нет. Создаются только технические настройки и исходные права доступа.

Имя первой миграции сохранено. На единственной существующей локальной установке журнал отдельно сокращён с 22 записей до одной. Штатный обновлятор Flarum после этого пропускает миграцию. Таблицы, персонажи, справочники, настройки и данные событий не изменялись.

Исторические файлы оставлены только в `tests/fixtures/migrations-2026-10-30/`. Они используются сценариями прежних преобразований и сравнением схем, а не обновлятором форума. Удаление расширения сохраняет принятые от QuestEvents таблицы обычных форумных событий, как и раньше.

Это объединение согласовано для проекта без внешних установок. Оно не является универсальным обновлением произвольной старой версии расширения.

## Замечания аудита

- MySQL/MariaDB сохраняют прежние CHECK-ограничения. Их специфичный SQL не выполняется на SQLite и PostgreSQL; проверки приложения остаются общими.
- Фильтр рас использует JSON-селектор Illuminate вместо `JSON_EXTRACT`.
- Инспектор прежних таблиц использует Schema Builder вместо `information_schema`. Имена берутся без квалификатора схемы, но с префиксом форума.
- Подключён официальный `flarum-tsconfig`. Типы установленного ядра подготавливаются через `npm run types:sync`; они не входят в Git.
- Шесть контроллеров персонажа получают сервисы через конструкторы. Привязка профиля к адаптеру форумных тем задаётся в `RoleplayServiceProvider`.

## Проверки

`tests/check-consolidated-schema.php` создаёт две изолированные схемы с временными префиксами: прежняя цепочка и новая миграция. Сравниваются поля, значения по умолчанию, индексы, внешние ключи, CHECK-ограничения, технические настройки и пять исходных разрешений. Имена индексов могут отличаться: SQLite требует их уникальности во всей базе.

Проверены перенос реального JSON справочников на новую схему, установка на SQLite, фильтр рас и инспектор SQLite, разрешение зависимостей контроллеров и удаление только таблиц Roleplay. Для PostgreSQL проверена генерация SQL; запуск на настоящем сервере PostgreSQL ещё не выполнялся.

Без локального файла `tests/.runtime/schema-consolidation-2026-10-30/catalogs.json` тест использует встроенное начальное наполнение. Произвольный экспорт можно передать через `ROLEPLAY_SCHEMA_CATALOGS`. Тест запускается только на тестовой копии с `ROLEPLAY_TEST_COPY=1`.

Дополнительно прошли серверные сценарии справочников, создания, анкеты, развития, выдач и обучения, проверки JSON-переноса, клиентская проверка админки, TypeScript и production-сборка.

## Локальные резервные копии

Вне расширения, в `C:\Forum\Flarum`:

- `output/schema-consolidation-2026-10-30/` — исходные миграции, SQL-снимок, контрольные суммы и отчёты проверки.
- `jsons/roleplay-catalogs-2026-10-30-before-schema-consolidation.json` — обычный экспорт всех справочников для импорта на новый форум.
- `jsons/roleplay-settings-2026-10-30-before-schema-consolidation.json` — резервная копия настроек создания, развития и прав. Это служебный снимок, а не файл импорта справочников. Настройки создания содержат ID записей: на другой базе их нужно сопоставить заново.

`tools/consolidate-local-migrations.php` выполняет одноразовую подготовку локального журнала. Перед записью он проверяет идентичность базы, SQL-снимок, подтверждение теста и неизменность всех доменных таблиц. Режим `apply-history` изменяет только журнал миграций Roleplay и проверяет штатный обновлятор. На новом форуме этот инструмент не нужен.

Для отката именно объединения на текущей базе достаточно вернуть старые файлы из архива и 22 строки журнала из `snapshot.json`: схема и игровые данные не менялись. SQL-снимок хранится отдельно на случай восстановления данных; для обычного отката журнала его применять не нужно.
