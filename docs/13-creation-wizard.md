# Мастер создания: интерфейс и дополнительные расовые владения

Мастер открывается в окне шириной 960 px из тегов «Ролевая» / «Анкеты» и профиля.
Отдельного маршрута `/roleplay/create` больше нет. Текущий и пройденные шаги заметные,
будущие — бледные. Полоска шагов и нижние кнопки остаются на месте, прокручивается содержимое.
На телефоне окно занимает почти весь экран.

Закрытие крестиком, Escape или кликом по фону дожидается сохранения черновика.
Если сохранить не удалось, ввод остаётся в открытом окне; можно повторить сохранение или явно закрыть без него.
Повторное открытие загружает сохранённый шаг. После создания открывается новая анкета в профиле.
При редактировании технической части применяется та же форма, но сам персонаж меняется только после финального подтверждения.

## Сценарий и макеты

Семь шагов: общие сведения → характеристики → навыки/владения → перки → заклинания → снаряжение → итог.

На первом шаге показываются имя, фамилия, возраст, раса и её фиксированные бонусы. Стрелка рядом с расой открывает настроенную страницу правил в новой вкладке. Без ссылки стрелка не выводится.

Характеристики распределяются кнопками ±. Интерфейс показывает остаток очков, расовые прибавки и приобретённые итоги. Игрок свободно распределяет 7 очков, каждое начальное значение — от 1 до 3 до расовых прибавок. Кнопки ограничивают запас и границы, сервер проверяет их повторно; промежуточные значения могут быть незавершёнными.

Навыки и обычные владения сгруппированы по характеристикам. Сервер возвращает отдельный список вариантов для каждого достигнутого порога. Можно оставить обычный выбор на будущее. После замены раннего выбора навыка его последующие повышения сбрасываются; выборы другой характеристики сохраняются.

Карточки горизонтальные, по две в строке; до 480px — по одной. Выбранная карточка имеет зелёную рамку и круглую зелёную галочку справа сверху. Повторное нажатие снимает выбор. При достижении лимита невыбранные карточки отключаются; выбранные остаются доступными для снятия. Enter и пробел работают с клавиатуры. Выделение текста описания не переключает выбор.

В перках сверху показаны выдаваемые способности, ниже — расовый выбор. В заклинаниях отдельно показаны автоматические, расовый выбор и обычный выбор. В снаряжении каждая группа имеет свой лимит; автоматические наборы показаны без выбора. Итог оформлен общей анкетой с реальными расчётами ресурсов, урона, защиты и веса.

## Настройка расовых владений

В редакторе расы появились:

- «Сколько владений выбрать» — proficiency_choice_count; 0 отключает блок.
- «Доступные владения» — proficiency_choice_mode: all или list.
- Список определений — proficiency_choice_ids, используется в режиме list.
- «Ссылка на правила расы» — rules_url, полная HTTP/HTTPS-ссылка без логина и пароля.

Для полуэльфа: mode = all, count = 1. Для дварфа: mode = list, count = 1, список ID одноручного и двуручного владений. Названия рас и конкретные ID не зашиты в код и не добавляются в миграцию.

Расовый выбор не проверяет уровень характеристики и не расходует обычные пороговые права. Используется только включённое определение владения из разрешённого расой списка. Полученное автоматически или ранее выбранное обычным способом владение не предлагается повторно. Сначала учитываются автоматические владения, затем расовый выбор, затем обычное обучение; дубликаты не создают вторую выдачу.

Поле черновика racial_proficiency_ids отделено от proficiencies. Количество и список проверяются сервером при сохранении предпросмотра и снова при окончательном создании. Реальная выдача использует существующую CreationGrants и общую транзакцию. Расовый выбор обязателен, если у расы count > 0; возможность оставить выбор на будущее относится к обычным пороговым правам.

Удаление владения из каталога блокируется, если оно используется в расовом списке. Выключение сохраняет определения и уже полученные владения, но запрещает новое получение.

## Одна система правил и расчётов

CreationOptions использует DevelopmentRules, SkillEligibility, ProficiencyEligibility и TrainingCreationPlan. Варианты повышения строятся по состоянию ДО соответствующего выбора: уже выбранный III уровень можно редактировать без ошибочного сообщения «навык на максимуме». Интерфейс не содержит второй таблицы порогов.

CreationValidator разделяет ошибки общих сведений и распределения характеристик. Благодаря этому первый шаг не требует заполнить будущие шаги.

CreationReview собирает CharacterSnapshot в памяти из доверенного плана и вызывает CharacterCalculationBuilder. Эффекты перков, доступные заклинательные атаки, максимумы ресурсов и вес рассчитываются тем же кодом, который используется для персонажа. Предпросмотр не делает выдач и не выполняет SQL. Стартовые вещи не экипируются автоматически; их эффекты в итог не применяются до экипировки.

## Сохранение и ошибки

Ввод сохраняется с задержкой 600ms. Одновременно идёт один запрос; ввод во время запроса отправляется следующим с новой версией. Старый ответ не заменяет последний ввод.

Перед переходом мастер сохраняет черновик и получает серверный предпросмотр. Назад можно перейти и при незавершённом текущем шаге. Дальше — только после завершения предыдущих шагов.

Конфликт двух вкладок останавливает автосохранение. Локальный ввод остаётся на экране; кнопка «Загрузить сохранённый черновик» явно загружает актуальное состояние. Изменение справочников также требует загрузить их актуальную версию.

После изменения расы/характеристик/справочников недоступные выбранные способности остаются доступными для снятия. Для ошибочного обычного обучения есть отдельные кнопки сброса навыков и владений. Устаревшие варианты/группы вещей также можно убрать.

Повтор создания после потери ответа отправляет тот же operation_key и те же версии. Двойное нажатие во время запроса отключено. После успеха мастер показывает подтверждение и имеющийся итог; после повторной загрузки сервер сообщает об уже созданном персонаже и блокирует новую выдачу. Переход на страницу профиля подключён следующим этапом; см. документ 14.

## Где редактировать

- Порядок, подписи и ключи иконок шагов — types.ts.
- Конкретный экран — соответствующий steps/*.tsx.
- Размеры окна, отступы, плашки, цвета характеристик и адаптивность — creation.css.
- Общие карточки — common/cards и cards.css.
- Иконки — icons.json; локальные замены Pro-иконок — icons.local.json, без миграций.
- Расовые бонусы/списки/количество/ссылка — редактор расы.
- Конкретные стартовые предметы и золото — серверные настройки создания, см. документ 12.

### Оформление мастера

На компьютере окно имеет ширину 960 px, на телефоне занимает весь экран.
Прокручивается только содержимое шага: заголовок, прогресс и действия остаются видимыми.
Для мобильного окна точечно убран резерв под полосы прокрутки, который добавляет Flarum.

Высота настольного окна — 92dvh (максимум 980 px с сохранением внешних отступов).
Верхняя шапка использует обычные шрифт и цвет общих модальных окон. Шрифты правил
применяются к содержимому, короткие пояснения используют системный muted-color.

Jost и Oracle подключены из тех же файлов, что используются в правилах.
Фон, поля и плашки наследуют системные цвета темы, а характеристики используют
согласованные цвета из правил. Карточки сущностей остаются общими с профилем.
Фрагменты `locations.jpg` видны по краям только на широком экране и не лежат под текстом.

Первый экран содержит вступление. Заголовки шагов и короткие пояснения центрированы,
тексты самих карточек сохраняют обычное выравнивание. Обычные навыки и владения
можно оставить невыбранными; обязательные расовые выборы проверяются как прежде.

Новая колонка rules_url добавлена в единственную базовую миграцию ещё не установленного пакета. Миграция не содержит ссылок, иконок, полуэльфа или дварфа как игровых данных.

## Проверки и ограничения

Серверные сценарии работают на временных таблицах с отдельным проверенным префиксом. Проверяются свободное и ограниченное расовые владения, отсутствие требований Магии, дубликаты, автоматическая выдача, реальное сохранение через API, варианты III ранга, независимость первого шага от будущих и общий расчёт веса/ресурсов.

Клиентский тест tests/check-creation-client.cjs использует вымышленные данные из tests/.runtime/creation-view.json, сформированные серверным сценарием. Он раскрывает все семь шагов настоящим Mithril, проверяет рамку/галочку, клавиатуру, отключённые карточки, устаревшие выборы, очередь сохранения, конфликт и повтор создания. Это проверка поведения и разметки, а не визуальная проверка в браузере.

Проверки запускаются после сборки нового JS. Для клиентского стенда нужна локальная карта tests/.runtime/core-admin.js.map установленного ядра Flarum; она не публикуется вместе с пакетом.

Пакет пока не установлен; новые каталоги ещё нужно заполнить и привязать стартовые наборы. Профиль и экипировка реализованы следующим этапом (документ 14). Интерфейс администрирования стартовых наборов, литературная анкета/модерация и последующая прокачка остаются отдельными этапами.


### Итог и аватар персонажа

`steps/ReviewStep.tsx` показывает краткие сведения, характеристики, навыки и владения,
а затем два списка перков и заклинаний. Полная `CharacterSheet` остаётся в профиле.

`CharacterAvatarUpload.tsx` — выбор, замена и удаление изображения.
`POST /api/roleplay/creation/avatar` доступен вошедшему игроку с правами создания.
Принимаются JPG, PNG, WebP до 2 МБ и 4096 × 4096 px. Сервер проверяет фактическое
содержимое, обрезает по центру до квадрата и перекодирует в 512 × 512 WebP.
Рекомендуемый исходник — квадрат от 512 × 512 px.

Черновик и персонаж хранят `avatar`: имя обработанного файла с ID загрузившего игрока
и случайным ключом. Внешние URL, чужие файлы и произвольные пути не принимаются.
Файлы лежат в диске `roleplay-images`, в `avatars/`. `characterAvatarUrl.ts` — общая
точка получения адреса с учётом подпапки форума. Публичный API профиля возвращает
`avatar`, а общая анкета отображает изображение. Исправление стартового выбора
восстанавливает текущий аватар и сохраняет новый вместе с остальными изменениями.

На время загрузки заблокированы переходы, создание и обычное закрытие. При ошибке прежнее
изображение остаётся в форме. Удаление из формы отвязывает файл только после сохранения.
При следующих загрузках убираются бесхозные аватары этого игрока старше недели,
при этом сохраняются файлы его персонажей и текущего черновика.

Подход к загрузке проверен по Arena `CardIdeaEditModal` / `UploadCardIdeaImageController`
(версия 6f65025). Roleplay не требует Arena: собственный обработчик и хранилище
работают при выключенной или удалённой Arena.

Проверки обновления 25.10.2026: TypeScript, production-сборка, изолированные
серверные сценарии (совместимость старых черновиков, права на файл, обрезка,
создание и редактирование с аватаром, публичный профиль) и клиентские сценарии.
Браузер: 7 экранов × 3 размера × 2 темы, загрузка настоящего файла, повторное
открытие, удаление, отказ некорректному файлу и гостю. Проверочные загрузки удалены,
персонажи и темы в основной базе не создавались.


### Плотность отдельных шагов и меню аватара

`fieldset.RpWizard-content` получает `data-step`: компактные отступы и размеры
настроены только для `attributes` и `training`, включая короткие настольные окна.
Первый экран сохраняет прежнее оформление. Активный плюс залит цветом характеристики.
У списков обучения отключена нативная стрелка, собственный шеврон отстоит от края на 16 px.

Размеры перков, заклинаний и предметов наследуются из общего `cards.css`
(основная часть 86 px, полоса 24 px). В `creation.css` нет конкурирующего размера.
Параметры заклинания занимают строку под названием, допускают перенос и не прокручиваются
по горизонтали. Вложенные карточки на плашках выбора используют фон body-bg
и тонкую обводку, чтобы не сливаться с окружением.

В итоговом экране `RpWizard-reviewSummary` ставит сведения с аватаром рядом с
характеристиками и навыками. На телефоне эти две панели идут последовательно.
Иконки заклинаний используют `pathColor` из справочника путей.

Отдельной кнопки загрузки нет: пустой аватар открывает выбор файла, заполненный —
меню «Заменить»/«Удалить». Меню монтируется соседним элементом `Modal-content`
внутри `.Modal`: его не обрезает прокрутка, и оно остаётся в области фокуса Flarum.
Стрелки переключают пункты, Escape закрывает только меню (включая перехват keyup,
по которому ядро закрывает модалку), щелчок вне меню, прокрутка или смена шага
также убирают его. Обработчики и отдельный Mithril mount удаляются при закрытии.

Проверка этой правки: 70 вариантов (7 шагов, 5 размеров, 2 темы). На настольных
окнах вплоть до 1024 × 668 проверен шаг характеристик с тремя расовыми выборами
и обучение с четырьмя слотами: прокрутки нет. Также проверены высота карточек,
отсутствие горизонтальной прокрутки параметров, фон вложенных карточек, цвета
путей, соседние панели итога и полный цикл меню аватара, включая клавиатуру.
На телефонах содержимое остаётся прокручиваемым при необходимости.

Знаки увеличения/уменьшения — небольшие встроенные SVG, центрированные grid
внутри кнопки: их положение не зависит от шрифтовой базовой линии.
Карточки ограничены 372 px (половина 760 px минус половина промежутка 16 px).
Автоматические предметы используют ту же `RpWizard-cardGrid`, а предметы внутри
выбираемого набора остаются вертикальным `RpWizard-bundle`. В прогрессе отступ
от линии к области значка равен 1 px, сама область — 30 px (28 px на телефоне).


### Открытие после загрузки данных

Все точки входа вызывают `CreationWizardModal.open(profile?)`. Метод сначала
загружает `CreationState` и только после успешного ответа передаёт готовое состояние
в модальное окно. `oninit` не выполняет повторный запрос. При ошибке показывается
обычное уведомление форума, окно не открывается, следующий клик повторяет загрузку.
Повторные клики во время запроса объединены. Ответ после смены страницы, аккаунта,
другого окна или выбранного персонажа не открывает устаревший мастер.

`tests/check-wizard-opening.cjs` проверяет ожидание ответа, повторные клики, один
запрос при открытии, ошибку/повтор, переход на другую страницу и загрузку редактора.
Браузером проверены отсутствие промежуточного окна при задержке, ошибка и повтор,
а также открытие готового шага на телефоне.


### Подтверждение создания и литературная тема

Кнопка «Создать персонажа» на итоговом шаге сначала сохраняет и проверяет
черновик, затем открывает `CreationConfirmationModal` поверх мастера.
В окне объясняется, что появится тема с именем персонажа и незаполненной
художественной анкетой. При необходимости игрок сначала готовит отдельную тему,
а после создания переносит из неё BB-код в тему, созданную мастером.

- «Создать персонажа» отправляет прежнюю атомарную команду создания
- «Оставить черновик» сохраняет выбор и закрывает оба окна без создания темы
- Крестик, Escape и фон закрывают только подтверждение и возвращают в мастер

Во время запроса повторные действия и закрытие заблокированы. При ошибке окно
остаётся открытым: повтор использует тот же operation_key и версии. После успеха
оба связанных окна закрываются через состояние менеджера Flarum, без ожидания
transitionend у скрытого мастера. Затем открывается профиль персонажа.
Сохранение уже существующей анкеты проходит без предупреждения о новой теме.

`tests/check-creation-confirmation.cjs` проверяет отсутствие создания до явного
согласия, возврат, сохранение черновика, закрытие двух окон и отдельное поведение
редактирования. В браузере проверены Escape, черновик, повторные клики, запрет
закрытия во время запроса, ошибка/повтор с тем же ключом и закрытие обоих окон
на телефоне. Запрос создания в браузерном тесте подменён: реальные персонажи
и темы для проверки не создаются.


### Действия в боковом меню ролевых тегов

В `addCreationButton.ts` для `role` и `characters` порядок следующий:
штатная «Создать тему» для персонала (`roleplayCanModerate`), затем общий блок
`RpTagButtons` — «Создать персонажа» и «Путеводитель». Создание персонажа
показывается вошедшему игроку с `roleplayCanCreate`; путеводитель доступен
и при недоступном создании. Кнопки занимают одинаковую ширину.

Цвет персонажа берётся из модели текущего тега в Flarum store. Используются
штатные `Button--tagColored` и `textContrastClass`, поэтому цвет текста
контрастирует с фоном в обеих темах. Путеводитель — обычная серая `Button`,
ведущая на `/role`. На телефоне действия остаются в потоке страницы.

Исходный `newDiscussion` скрыт через `RpSidebarItem--hidden`, но не удалён
из ItemList: flarum-tags продолжает обращаться к этому узлу. Для персонала
показывается его копия с исходным обработчиком и ограничениями, с приоритетом 110.
Блок персонажа/путеводителя имеет приоритет 100. Отдельная прежняя ссылка
`roleplayGuide` в этих двух тегах убирается, на остальных страницах сохраняется.
Права создания обычных тем на сервере не меняются.

`tests/check-creation-button-client.cjs` проверяет оба тега, порядок, цвет,
права видимости и сохранение исходного действия создания темы. В браузере
проверены обе темы, компьютер и телефон, одинаковая ширина и цвет из тега.
